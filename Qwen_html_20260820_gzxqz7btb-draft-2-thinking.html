[ PHASE 00 ] MISSION BRIEFING

YOU CONVERT THE DISK. NOT THE VM.

A Hyper-V export bundles virtual disks, configuration files and checkpoint files. VMware and VirtualBox cannot read Hyper-V's .vmcx configuration — so the operation is always the same: extract the virtual hard disk, convert it to the target runtime's format, then build a fresh VM shell around it. Two runtimes, two conversion tools, one source payload.

[ PHASE 01 ] RECONNAISSANCE — SHARED BY BOTH PATHS

SURVEY THE EXPORT BEFORE YOU TOUCH IT

Every failed migration in this lab traces back to a skipped recon step. Run these four checks on the raw Hyper-V export before either conversion path. Both PATH_A and PATH_B assume this phase is complete.

R.1

operator@lab:~$MAP THE EXPORT STRUCTURE

A clean Hyper-V export lands in three folders. Microsoft confirms an export contains the virtual disks, configuration files and any checkpoint files — disks sit in Virtual Hard Disks. Only one of these folders matters to your target sandboxes:

EXPORT TOPOLOGY
D:\HyperV-Export\
├── Virtual Machines\
│   ├── <GUID>.vmcx        # Hyper-V config — IGNORE
│   ├── <GUID>.vmgs        # Hyper-V state  — IGNORE
│   └── <GUID>.vmrs        # Hyper-V state  — IGNORE
├── Virtual Hard Disks\
│   └── abcd2.vhd          ◄── THE PAYLOAD. THIS IS WHAT WE EXTRACT.
└── Snapshots\             # ◄── SCAN THIS FOLDER NEXT
R.2

operator@lab:~$SWEEP FOR CHECKPOINT DISKS

Inside Virtual Hard Disks\ and Snapshots\, look for .avhd / .avhdx files. Those are Hyper-V checkpoint (differencing) disks — each one stores changes layered on top of a parent disk:

CHECKPOINT CHAIN — IF DETECTED
abcd2.vhd                    ◄── base disk (an OLDER state)
   ▲
   └── abcd2-checkpoint1.avhd
              ▲
              └── abcd2-checkpoint2.avhd   ◄── CURRENT state lives up here
POWERSHELL — LIST EVERY DISK IN THE EXPORT
PS C:\> Get-ChildItem "D:\HyperV-Export\Virtual Hard Disks" | Select-Object Name, Length
⚠ CRITICAL — HALT CONDITION If any .avhd/.avhdx is present, do not convert anything yet. Converting only the base .vhd resurrects an outdated state of the specimen — missing files, missing configs, wrong results. Consolidate the chain first (merge checkpoints in Hyper-V before exporting, or ask your instructor for the disk-chain consolidation procedure).

If you see exactly one plain .vhd and nothing else — sweep is clear. Proceed.

R.3

operator@lab:~$QUARANTINE A BACKUP COPY

The original export is your fallback evidence — never modify it. Stand up working directories for each target and keep the source disk read-only in spirit:

DIR LAYOUT AFTER BACKUP
D:\HyperV-Export\    ◄── original, UNTOUCHED (your backup)
D:\HyperV-Backup\    ◄── optional second copy, recommended
D:\VirtualBox\MyVM\  ◄── PATH_A working dir → will hold MyVM.vdi
D:\VMware\abcd2\     ◄── PATH_B working dir → will hold abcd2_vmware.vmdk
◮ LIVE-DISK WARNING Never convert a disk that a running VM is using. QEMU's own documentation warns that modifying an image while another process holds it can destroy the image. Power off the Hyper-V specimen first.
R.4

operator@lab:~$IDENTIFY THE GENERATION (FIRMWARE PROFILE)

Hyper-V VMs are Generation 1 (BIOS firmware) or Generation 2 (UEFI firmware). Generation is a property of the VM, not the disk — you cannot tell by staring at the .vhd. If the original Hyper-V VM still exists, interrogate it:

POWERSHELL — QUERY VM GENERATION
PS C:\> Get-VM "abcd2" | Select-Object Name, Generation, State
#  Name   Generation   State
#  -----  ----------   -----
#  abcd2  2            Off      ◄── Generation 2 = UEFI

Record the result — both sandboxes must be configured to match, or the specimen will not boot:

HYPER-VFIRMWAREVIRTUALBOX SETTINGVMWARE SETTING
Generation 1BIOSEFI stays disabledFirmware type → BIOS
Generation 2UEFIEnable EFI ✓ (System → Motherboard)Firmware type → UEFI

Also in Hyper-V Manager: right-click VM → Settings shows generation/firmware if you prefer the GUI.

[ PHASE 02 ] EXECUTION — SELECT CONVERSION PATH

CHOOSE YOUR SANDBOX. EXECUTE.

Two independent deployment routes out of the same Hyper-V export. Run both — a malware analyst keeps redundant detonation environments. Each path is self-contained from the moment recon is done.

☣ A

TARGET: ORACLE VIRTUALBOX. Weapon of choice is VBoxManage.exe, VirtualBox's command-line interface. We clone the .vhd into VirtualBox's native .vdi format — leaving the original export untouched as fallback.

A.1

$VERIFY THE TOOLCHAIN — LOCATE VBoxManage.exe

On Windows it normally lives at C:\Program Files\Oracle\VirtualBox\VBoxManage.exe. Sweep the directory:

POWERSHELL
PS C:\> Get-ChildItem "C:\Program Files\Oracle\VirtualBox" -Force

You should see VirtualBox.exe, VBoxManage.exe, VBoxHeadless.exe among the files.

⚠ IF VBoxManage.exe IS MISSING Do not hunt for a standalone VBoxManage.exe download. Oracle's docs identify the VirtualBox application component as the carrier of the main binaries — it must not be omitted. Repair/reinstall VirtualBox from Oracle's official installer, then re-sweep the folder.
POWERSHELL — FOLDER MISSING ENTIRELY? HUNT THE INSTALL
PS C:\> Get-Command VirtualBox.exe -ErrorAction SilentlyContinue
PS C:\> Get-ChildItem "C:\Program Files" -Filter "VirtualBox.exe" -Recurse -ErrorAction SilentlyContinue
A.2

$TEST-FIRE THE BINARY

POWERSHELL
PS C:\> & "C:\Program Files\Oracle\VirtualBox\VBoxManage.exe" --version
# expected output: e.g. 7.1.x  ← any version number means the tool is armed

The & is PowerShell's call operator — required when executing a quoted path. If you get "not recognized as an internal or external command", the binary is absent → return to A.1.

A.3

$CONFIRM THE PAYLOAD PATH

POWERSHELL
PS C:\> Test-Path "D:\Hyper-V Export\MyVM\Virtual Hard Disks\MyVM.vhd"
# True  → target acquired
# False → path is wrong; use File Explorer to locate the real .vhd

Why the quotation marks? Paths like D:\Hyper-V Export\...\Virtual Hard Disks\ contain spaces. Without quotes, PowerShell reads the spaces as argument separators and the command fragments. Quotes weld the whole path into a single argument. This rule applies to every command in this manual.

A.4

$EXECUTE THE CONVERSION — VHD → VDI

Create the destination folder first (D:\VirtualBox\MyVM\), then fire the clone:

POWERSHELL — THE MAIN EVENT
PS C:\> & "C:\Program Files\Oracle\VirtualBox\VBoxManage.exe" clone medium disk "D:\Hyper-V Export\MyVM\Virtual Hard Disks\MyVM.vhd" "D:\VirtualBox\MyVM\MyVM.vdi" --format VDI
  • 1st quoted path → source (.vhd)
  • 2nd quoted path → destination (.vdi)
  • --format VDI → output in VirtualBox's native disk format

A progress readout crawls from 0% ... 100%. Duration scales with disk size, drive speed and CPU. Walk away. Do not delete the original .vhd while it runs — or ever, for now.

⚠ RE-VERIFY BEFORE FIRING If your recon in R.2 surfaced any .avhd/.avhdx files, abort. You would be cloning only the base disk — an old state of the specimen.
A.5

$CONFIRM THE .VDI MATERIALIZED

POWERSHELL
PS C:\> Test-Path "D:\VirtualBox\MyVM\MyVM.vdi"
# True → payload delivered
PS C:\> Get-Item "D:\VirtualBox\MyVM\MyVM.vdi" | Select-Object Name, Length, FullName

Sanity-check the size. A suspiciously tiny Length means the conversion went sideways.

A.6

$FORGE THE VM SHELL IN VIRTUALBOX

Open VirtualBox → New. This shell mimics the original Hyper-V hardware profile:

  • Name: same or similar to the original (e.g. MyVM)
  • Type / Version: match the OS already inside the disk — e.g. Microsoft Windows → Windows 11 (64-bit)
  • RAM: mirror the Hyper-V allocation (4096 MB → 4096 MB; 8192 → 8192). Adjustable later
  • CPU: match the virtual processor count (e.g. 4), but never hand the VM every physical core
◮ DO NOT INSTALL AN OS We are not installing Windows again. The installation already lives inside your .vdi.
A.7

$ATTACH THE CONVERTED DISK

When the wizard asks about a virtual hard disk → Use an Existing Virtual Hard Disk File → browse to D:\VirtualBox\MyVM\MyVM.vdi.

Already built the VM without a disk? Select the VM → Settings → Storage → pick the storage controller → Add Hard Disk → Choose Existing Disk → select your .vdi.

Under Settings → Storage, a conventional setup (disk on a SATA controller) is the goal. When migrating an existing Windows installation, resist the urge to tinker — change one variable at a time.

A.8

$SET THE FIRMWARE (RECON R.4 PAYS OFF HERE)

Settings → System → Motherboard:

  • Original was Generation 2 / UEFI → tick Enable EFI
  • Original was Generation 1 / BIOS → leave EFI off
  • While you're there: check Boot Order — Hard Disk enabled and above optical/network
⚠ GET THIS WRONG AND… …you'll stare at "No bootable medium found" even though the .vdi holds a perfectly live Windows installation. See INCIDENT INC-01.
A.9

$NETWORK: NAT FIRST

Settings → Network → Adapter 1 → Enable Network Adapter → Attached to: NAT. NAT gives the specimen simple outbound internet with zero LAN exposure — correct posture for a first boot. Switch to Bridged Adapter later only if the VM must appear as a real host on your physical network.

A.10

$DETONATE — FIRST BOOT

Click Start. Expect turbulence: the first boot runs long because Windows is discovering an entirely new virtual hardware set — fresh storage controllers, NIC, firmware. Driver installations and brief weirdness are normal. Let Windows finish. Do not force-reset mid-discovery.

✓ MISSION SUCCESS STATE Windows boots → migration is essentially complete. You now run: Hyper-V export (MyVM.vhd) → VBoxManage clonemedium → MyVM.vdi → VirtualBox VM. Keep the original .vhd until the VirtualBox VM is proven stable.

Blue screen instead? The specimen crossed hardware universes — log the exact stop code and proceed to INCIDENT INC-02 before assuming the disk is dead.

A.11

$OPTIONAL :: SKIP CONVERSION ENTIRELY

Conversion is not strictly mandatory — VirtualBox can mount .vhd directly, and clone medium also speaks VMDK, VHD, RAW and more. But for a migration, Option A (→ VDI) is recommended: native format, independent copy, original Hyper-V disk untouched.

POWERSHELL — IF VIRTUALBOX CALLS THE .VDI "INACCESSIBLE"
PS C:\> & "C:\Program Files\Oracle\VirtualBox\VBoxManage.exe" showmediuminfo "D:\VirtualBox\MyVM\MyVM.vdi"
☣ B

TARGET: VMWARE WORKSTATION. Weapon of choice is qemu-img.exe, QEMU's offline image converter. We forge a .vmdk from the Hyper-V .vhd, then let VMware Workstation build the .vmx shell around it.

B.1

$DEPLOY THE CONVERTER — QEMU'S qemu-img

Obtain qemu-img.exe (e.g. the Cloudbase Windows build: https://cloudbase.it/qemu-img-windows/) and drop it somewhere sane, e.g. C:\Program Files\qemu\. Test-fire it:

POWERSHELL
PS C:\> qemu-img.exe --version
# if "not recognized" → it's not on PATH. Invoke with the full path instead:
PS C:\> "C:\Program Files\qemu\qemu-img.exe" --version

A version number means the tool is armed. QEMU documents qemu-img as an offline image converter supporting VHD (vpc) and VMDK among its formats.

B.2

$INTERROGATE THE SOURCE DISK

POWERSHELL
PS C:\> qemu-img.exe info "D:\HyperV-Export\Virtual Hard Disks\abcd2.vhd"

Confirm QEMU reports the format as vpc (its name for VHD) plus virtual/disk size. Quotes are mandatory — Virtual Hard Disks contains spaces that would otherwise shred the argument.

B.3

$EXECUTE THE CONVERSION — VHD → VMDK

Create D:\VMware\abcd2\ first, then:

POWERSHELL — THE MAIN EVENT
PS C:\> qemu-img.exe convert -p -f vpc -O vmdk "D:\HyperV-Export\Virtual Hard Disks\abcd2.vhd" "D:\VMware\abcd2\abcd2_vmware.vmdk"
SWITCHFUNCTION
convertrun the disk conversion operation
-pshow progress
-f vpcsource format = VHD
-O vmdkoutput format = VMDK (capital O — that's "output", not a zero)

Progress ticks upward; duration depends on disk size and drive speed. When it lands you'll own D:\VMware\abcd2\abcd2_vmware.vmdk.

⚠ CHECKPOINT CHAIN REMINDER .avhd/.avhdx present? Stop. Converting only abcd2.vhd clones an older state of the specimen. Resolve the chain first (PHASE 01 / R.2).
B.4

$VERIFY THE VMDK BEFORE TRUSTING IT

POWERSHELL
PS C:\> qemu-img.exe info "D:\VMware\abcd2\abcd2_vmware.vmdk"
# expected:  file format: vmdk  + virtual size / disk size readout

If QEMU can read its own output, the disk structure is sound. If it can't — the conversion failed; rerun before blaming anything else.

B.5

$FORGE THE VM SHELL — WIZARD, CUSTOM MODE

In VMware Workstation: File → New Virtual Machine. This is where most operators go wrong, so follow exactly:

  1. Choose Custom (advanced) → Next (lets you control hardware compatibility; the default/recommended compatibility is fine)
  2. Guest OS screen → select "I will install the operating system later" — you are not installing anything; an OS already inhabits the .vmdk
  3. Pick the OS already inside the disk — e.g. Microsoft Windows → Windows 11 x64, or Windows Server 2022. Know your bitness: plain "Windows 10" = 32-bit, "Windows 10 x64" = 64-bit
  4. Name it (e.g. abcd2_vmware) and point the location at D:\VMware\abcd2\ — somewhere with real free space
B.6

$PROVISION CPU / RAM / NETWORK

  • CPU: roughly mirror Hyper-V — e.g. 4 virtual processors → 1 processor × 4 cores (or equivalent)
  • RAM: match the original (8192 MB → 8192 MB), but don't starve your Windows host
  • Network: NAT for the first boot — simplest and safest. Bridged / Host-only later as needed

You don't have to reproduce Hyper-V's exact virtual hardware — approximate is correct.

B.7

$THE DECISIVE SCREEN — SELECT A DISK

  1. At Select a Disk choose Use an existing virtual disk → Next
  2. Browse → D:\VMware\abcd2\ → select abcd2_vmware.vmdk → Next
  3. If asked whether to Keep Existing Format or Convert → Keep Existing Format. The disk is already converted; no gratuitous re-conversions
  4. Finish the wizard

VMware now generates the file set — abcd2_vmware.vmdk, abcd2_vmware.vmx, .nvram, logs. The critical artifact:

KNOW YOUR FILES
abcd2_vmware.vmdk   = the virtual HARD DISK  (do NOT double-click)
abcd2_vmware.vmx    = the VM CONFIGURATION   (THIS is what you open)
◈ WHY YOU SAW THAT ERROR BEFORE "abcd2_vmware.vmdk cannot be opened directly. Open the virtual machine configuration file (.vmx) instead." — that message is correct behavior. The VMDK is a disk; the VMX is the machine. Broadcom's documented procedure is exactly this: create a new VM and point it at the existing VMDK.
B.8

$SET FIRMWARE TO MATCH THE GENERATION

VM → Settings → Options → Advanced → Firmware type:

  • Hyper-V Generation 1 → BIOS
  • Hyper-V Generation 2 → UEFI

If the original Gen 2 VM used Secure Boot, don't juggle it immediately. First establish UEFI + correct VMDK + correct boot device; only if the VM still refuses to boot, revisit Secure Boot under Options. Then check Options → Advanced → Boot Options and make sure the hard disk is a live boot candidate.

B.9

$DETONATE — FIRST BOOT

Confirm under VM → Settings → Hard Disk that the disk file points at D:\VMware\abcd2\abcd2_vmware.vmdk, then Power on this virtual machine. Expected boot chain: VMware → UEFI/BIOS → Windows Boot Manager → Windows. The first boot is slow — Windows is meeting brand-new virtual hardware. Be patient.

✓ POST-BOOT HARDENING SEQUENCE 1. Install VMware Tools once Windows is up (guest drivers + integration), then reboot · 2. Win+X → Device Manager — hunt yellow warnings / unknown devices · 3. Verify networking (ipconfig; NAT should give you internet) · 4. Expect possible Windows reactivation — the hardware fingerprint changed, and migration does not automatically preserve activation.
[ PHASE 03 ] INCIDENT RESPONSE — TROUBLESHOOTING DOSSIER

KNOWN FAILURE MODES & COUNTERMEASURES

Filed from actual migration attempts. Before you panic-reinstall anything, match your symptom against the dossier. Nine times out of ten it's firmware, attachment, or the checkpoint chain.

INC-01SEV: CRITICAL

"No bootable medium found"

PATH_A :: VIRTUALBOX

The disk holds a live OS but the shell can't boot from it. Almost always firmware mismatch.

FIX ► A. Gen 2 source? Enable EFI (Settings → System → Motherboard). B. Verify the .vdi is actually attached under Storage. C. Boot Order — Hard Disk enabled and first.
INC-02SEV: HIGH

Windows blue-screens on first boot

PATH_A + PATH_B

Don't assume disk corruption. The specimen jumped hypervisors — new storage controllers, CPU presentation, firmware, NIC. Windows can choke on the delta.

FIX ► Photograph the exact stop code. Check firmware setting and disk controller type. Do not reinstall Windows — preserving this installation is the whole mission.
INC-03SEV: HIGH

'VBoxManage' is not recognized…

PATH_A :: VIRTUALBOX

The binary is missing or VirtualBox was installed without its main application component.

FIX ► Sweep C:\Program Files\Oracle\VirtualBox. If absent, repair/reinstall VirtualBox from Oracle's official installer — never download VBoxManage.exe standalone. See step A.1.
INC-04SEV: MEDIUM

VirtualBox reports the .VDI is "inaccessible"

PATH_A :: VIRTUALBOX

VirtualBox can't parse the medium's metadata.

FIX ► Interrogate it: VBoxManage.exe showmediuminfo "…\MyVM.vdi". If the tool can't read it either, the conversion is suspect → rerun step A.4.
INC-05SEV: CRITICAL

".vmdk cannot be opened directly"

PATH_B :: VMWARE

You double-clicked the disk. The VMDK is storage, not a machine definition.

FIX ► Open abcd2_vmware.vmx instead — or open Workstation and load the VM from there. If no .vmx exists, run the wizard again and point it at the existing VMDK (step B.5–B.7).
INC-06SEV: CRITICAL

"Operating System not found"

PATH_B :: VMWARE

VMware's firmware can't see a bootable target.

FIX ► Match firmware to generation (Gen 1 → BIOS, Gen 2 → UEFI). Confirm the correct VMDK is attached. If the source had a checkpoint chain, you may have converted only the stale base disk.
INC-07SEV: HIGH

Windows Boot Manager never appears

PATH_B :: VMWARE

Firmware fires, but nothing bootable answers.

FIX ► Verify in order: firmware type → boot device → VMDK attachment → partition type → that you converted the final Hyper-V disk. Do not start Windows repair until all five check out.
INC-08SEV: CRITICAL

Booted — but the data is from the past

PATH_A + PATH_B :: CHECKPOINT CHAIN

Specimen "works" yet files/settings are stale. An .avhd/.avhdx chain existed and only the base .vhd got converted.

FIX ► Consolidate the chain (merge checkpoints in Hyper-V, re-export) and convert again. This is why R.2 is non-negotiable.
INC-09SEV: MEDIUM

qemu-img.exe "is not recognized"

PATH_B :: VMWARE

The converter isn't on your PATH.

FIX ► Invoke it by full path — "C:\Program Files\qemu\qemu-img.exe" --version — or add its directory to PATH.
